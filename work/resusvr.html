Scenario work

Medical training content is unusually unforgiving: a scenario has to be clinically correct before it is allowed to be good software. I designed and implemented scenarios spanning varied emergency situations and patient age groups — and paediatric and adult cases are not the same content with a different model, they differ in protocol, in timing, and in what counts as a correct action.

That constraint pushes the implementation toward data. When the difference between two scenarios is a set of clinical parameters rather than a set of behaviours, the scenarios become authorable and reviewable by the people qualified to review them, instead of being buried in code only an engineer can audit.

The localisation pipeline

The product shipped in multiple languages, and localisation was a manual process — export, send, receive, re-import, verify, discover the strings that were missed, repeat. It cost real money per release and, worse, cost time on the critical path of every release.

I automated it. The measurable result was reduced turnaround time and reduced cost on every release afterwards; the structural result was that adding a language stopped being a decision and became a setting.

This is the work I point at when someone asks whether I only care about engine internals. Nobody demos a localisation pipeline. It was still the highest-leverage thing I could build on that project, because it removed a recurring cost from every future release rather than a one-off cost from this one.
