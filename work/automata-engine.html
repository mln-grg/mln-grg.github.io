automata-engine

Conway's Game of Life on a 1920 by 1080 grid, written in C++20 with SDL2. Two million cells simulated and drawn every frame, with a live readout of how long each of those two things took. The rules and the visuals are finished. The inner loop is not, and that is the point.

C++20, SDL2
Grid
2,073,600 cells
Version
1 of a planned 4
Source
github.com/mln-grg/automata-engine

Why build this at all

Life is a solved problem. What is not solved is my ability to say, from memory and with numbers, what the difference is between arranging work better and doing less work. Those two things get conflated constantly in interviews, including by me. So the plan is four versions of the same program, benchmarked on the same machine with the same flags, seed and grid size, and a record of what I predicted before each measurement and what I actually got.

Where it stands

Version one is the obvious one, and it is what is on GitHub today. On an i7-12700F, release build, the readout sits at roughly:

  • SIM 14.3 ms, the simulation step
  • DRAW 1.6 ms, filling the pixel buffer
  • MCELLS/S 145, millions of cell updates per second
  • FPS 51.8

Everything after this is a rewrite of the inner loop with the same rules and the same output.

The four versions

  1. Naive. The obvious implementation, allocating as it goes.
  2. Mechanical sympathy. A flat vector<uint8_t> indexed y*W+x, both buffers allocated once. Identical algorithm. Every gain comes from cache locality and from not allocating in the hot loop.
  3. Algorithmic. Bit pack 32 cells into a uint32 and compute all 32 at once with bitwise full adders on the neighbour counts. Less work, not better arranged work.
  4. Parallel. The grid lives in a texture, a fragment shader reads eight neighbours and writes the next state to a second texture, ping ponged, never read back to the CPU.

Two things would invalidate the headline number, so they are rules rather than intentions. Every version gets benchmarked on the same machine, flags, seed and grid size, because a debug versus release comparison is worth about ten times on this loop and an interviewer catches it in one question. And vsync goes off before the GPU version is measured, or the answer is 60 generations a second and the conclusion is wrong.

Patterns are data, not code

Every pattern loads at startup from patterns/ as an RLE file, the format Golly and the LifeWiki use. Nothing is hard coded. There are 22 in the folder now, from a glider up to a switch engine breeder, and dropping a new .rle in there is the entire process for adding one. Left drag paints cells, the number keys stamp patterns under the cursor, the wheel zooms while keeping the cell under the cursor fixed.

The architecture rule

The grid is a flat std::vector<uint8_t> indexed y*W+x, never a vector of vectors, and the simulation step is a function that knows nothing about rendering. That was decided at version one specifically so version four is a swap rather than a rewrite.
