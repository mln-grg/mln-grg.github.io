Dynamic UI Framework

The UI framework for Project Greenleaf, built as its own C++ plugin. Gameplay writes state onto ViewModels, widgets subscribe to it by gameplay tag, and neither side ever holds a reference to the other.

01 — the boundary

MVVM, and what it buys

  • The ViewModel is the only type that knows both sides. Gameplay writes state onto it, widgets read state off it, and neither can reach the other directly.
  • A ViewModel holds properties and commands. It holds no widget pointers and calls no UMG functions, so it can be driven and inspected without a UI on screen.
  • A widget declares what it wants to display and the framework connects it. Adding a screen is editor work, not a change to the system the screen reports on.
  • That was the point of the rebuild. A new panel used to mean touching gameplay code, and that is where most of the UI bugs were coming from.
02 — contextual UI

ViewModel context & selection resolver

  • Some UI is permanent: level, health, XP, gold. Some of it depends entirely on what the player just clicked. The context owns both, the persistent player ViewModel and whichever contextual ViewModel the current selection produced.
  • A settlement, a hero and an agent each need a completely different screen. The Selection Resolver turns the selected actor into an FViewDescriptor: which view to show, and which ViewModel it runs on.
  • So the HUD carries no type checks. It reads a ViewType and looks up a widget class, and never learns which gameplay class produced it.
  • A new selectable thing costs a ViewModel and one resolver entry. Nothing in the HUD or in the existing widgets moves.
03 — composition

HUD composition & view lifecycle

  • The HUD is the one place that maps ViewType to widget class, and the one place that creates a view or tears it down.
  • If the descriptor arrives with a different ViewType, the old view goes and the new one is created.
  • If only the ViewModel changed, the view stays and is reinitialised with the new one. Clicking down a row of settlements costs a rebind, not a rebuild.
  • View lifetime and ViewModel lifetime are separate concerns, which is the thing that makes the second case possible at all.
04 — the binding layer

Gameplay tags & a TVariant value

  • Bindable properties are identified by gameplay tag rather than by string. They autocomplete, they are structured, and they cannot be typo'd into silence.
  • Values travel as a TVariant over an explicit supported set. Unreal already solves type erasure, copying and lifetime here, so I did not write my own.
  • The ViewModel stores a TMap<FGameplayTag, FBindingValue> and broadcasts the tag and the value on change. It never learns who is listening, and one property can drive several widgets at once.
  • The Binding Resolver is the single place that knows UMG. It pulls the expected type out of the variant and makes the call. A mismatch fails loudly instead of leaving a panel quietly showing nothing.
using FBindingValue = TVariant<float, int32, bool, FText, UTexture2D*>;

// gameplay side, no widget in sight
ViewModel->SetValue(TAG_UI_Hero_HealthPercent, 0.75f);

// view side, inside OnBindingChanged(Tag, Value)
HealthBar->SetPercent(Value.Get<float>());
05 — the way back

Two-way bindings & commands

  • Two-way binding is for a value the player edits, a volume slider being the plain case. The view can write, but only to the ViewModel, and the ViewModel decides what reaches the model.
  • A command is an operation. A heal button carries a command tag and knows nothing about how healing is implemented.
  • A command also reports whether it can run right now, so a greyed out button is derived from ViewModel state instead of being set by hand in three places.
  • Two-way binding needs a defined source of truth or the view and the model sit there updating each other. The ViewModel is it.
