Project Greenleaf

A Total War style strategy game in Unreal Engine 5: a campaign overworld feeding real-time battles with thousands of soldiers on the field at once. I joined as a gameplay programmer and ended up leading the battle and overworld layers — architecture, systems design, implementation, task breakdown and code review for a team of five.

01 — shipped as a standalone plugin

Battle simulation at scale

The problem

A Total War style battle wants two things that pull against each other. Every soldier should be a real individual — its own position, its own target, its own morale state, its own death — because that is what makes the line break believably rather than as one animated blob. And there should be thousands of them, at a playable frame rate, on hardware people actually own.

The default Unreal answer is an actor per soldier. That answer does not survive contact with 4,000 of them. Each actor carries a component hierarchy, a tick registration and a scene proxy; the simulation ends up chasing pointers across scattered heap allocations, and the renderer ends up with thousands of individual draw calls. The cost is not one bottleneck you can optimise — it is the shape of the data.

The shape of the solution

I split each soldier in two. Simulation lives in Unreal's Mass Entity framework, where a soldier is an entity: a row of tightly packed fragments processed in bulk, with no actor, no tick and no component tree. Presentation lives in a deliberately thin actor that owns nothing but the visual representation and reads its state from the simulation.

That split is the whole design. Everything that runs for every soldier every frame — movement, steering, target acquisition, formation slotting — runs in cache-friendly batches inside Mass processors. Everything that only needs to look right runs on the presentation side, where a slightly less efficient object model costs nothing because it is not the hot path.

Simulation: entities, not objects

Soldiers are entities composed of fragments — transform, velocity, formation slot, combat stats, target handle. Processors run over whole archetypes in bulk, so a movement pass walks a contiguous array of transforms instead of dereferencing four thousand scattered objects. This is the part of the design that is genuinely load-bearing: the win comes from memory layout and batching, not from micro-optimising any single routine.

Presentation: a thin actor with a state machine

Each soldier's visual state — idle, run, charge, melee attack, death, wall climb — is a plain C++ state object, pooled rather than allocated, entered and exited as the simulation changes. Entering a state starts an animation, either looping or one-shot, and one-shot animations route their completion back through a single callback so state transitions stay in one place instead of being scattered across animation events.

Rendering: instancing plus vertex animation

Skeletal meshes are the obvious way to animate a soldier and the wrong way to animate four thousand. The crowd renders as instanced static meshes with their animation baked into textures, so the GPU plays animation without a per-soldier skeleton on the CPU. Per-instance custom data channels carry what varies between soldiers: which animation is playing, how far through the death sequence it is, which weapon it holds, and the faction colour tinting it. Whole regiments end up costing a handful of draw calls.

Shipping it as a plugin

The battle layer lives in its own Unreal plugin, not in the game module. That was a deliberate call early on: it forces the dependency to point one way, keeps the battle testable without loading the campaign, and leaves the studio with reusable in-house technology rather than a system welded to one title.

Decisions I would defend

  • Hybrid, not pure ECS. A fully data-oriented presentation layer would have been faster on paper and considerably slower to build, debug and hand to other engineers. Keeping a thin actor per soldier preserved the parts of the engine — animation tooling, debugging, designer-facing workflow — that the team actually needed, at a cost that stays off the hot path.
  • Pooling over spawning. Battles create and destroy soldiers constantly. Pooling the presentation side removed the allocation spikes, and taught me that pooling buys performance in exchange for lifetime bugs: reused objects hold stale references, and you pay for the win with disciplined re-initialisation.
  • Measured, not guessed. Unreal Insights drove the optimisation work across the simulation, navigation and rendering paths. Every claim on this page came out of a capture, including the ones that told me my first instinct was wrong.

What I would do differently

The seam between simulation and presentation is the most expensive lesson in the project. Two systems owning halves of the same conceptual object means every lifetime edge case — pooling, level transitions, mid-battle streaming — has to be reasoned about twice. If I built it again I would define that seam as an explicit, narrow contract from day one, rather than letting it grow organically as each new requirement crossed it.

02 — used across the whole project

Data-driven UI framework

The problem

A strategy game is mostly interface, and the naive Unreal pattern is that gameplay code finds a widget and pushes values into it. It works for one HUD and rots immediately afterwards. Gameplay systems accumulate widget references they should never have owned; a widget that is destroyed, pooled or simply not created yet becomes a crash or a silent no-op; the same value gets pushed from four places with four slightly different formatting rules; and every new panel is an engineering task because only an engineer can wire it.

On a strategy title that last point is the expensive one. If designers cannot build a panel without a programmer, interface iteration runs at programmer speed, and the interface is the game.

The design

I inverted the dependency. Gameplay systems write to shared data models — plain objects holding named fields. Widgets subscribe to a field by name and update themselves reactively when it changes. Gameplay never knows a widget exists; a widget never reaches into gameplay. The binding layer between them is the only thing that knows about both.

Type dispatch, so any widget class can bind

A binding is not hard-coded per widget type. The layer dispatches on the type of the bound field and the type of the target, so a float can drive a progress bar, a text block or a custom widget nobody had written when the framework was built. New widget classes join the system without editing the system.

Blueprint-exposed, so designers own the wiring

The full API is exposed to Blueprint. A designer creates a widget, names the field it should follow, and it is live — no engineering ticket, no recompile, no programmer in the loop. This was the point of the whole exercise, and the measure of whether it worked: interface work stopped queueing behind engineers.

Subscription, so lifetime stops being a crash source

Because widgets subscribe and unsubscribe rather than being handed out as pointers, a widget that does not exist yet, or has already been torn down, is simply not in the notify list. An entire category of null-reference bugs stops being possible rather than being handled.

Decisions I would defend

  • Fields by name, not by compile-time binding. The tradeoff is real: a typo in a field name is a runtime problem, not a compiler error. I took it because the alternative puts every UI change back in C++, which was the exact cost the framework existed to remove.
  • Reactive push, not per-frame polling. Panels update when a value changes, not every tick. On a strategy HUD with dozens of live readouts, that difference is measurable and it scales with how elaborate the interface gets.
  • Built as framework, not as feature. It cost more up front than hard-wiring the first three panels would have. It paid that back by the time the project had thirty, and again every time a designer built one without me.
03 — part of the battle plugin

Grid navigation & formations

The problem

Unreal's built-in navigation is built for a modest number of agents that each want their own path, recomputed when the world changes. Point it at four thousand soldiers and the cost is not subtle. Worse, the result is wrong even when it is fast: individually pathed soldiers arrive as a stream of separate men trickling around obstacles, which is exactly the thing a line-battle game must not look like.

The design

Navigation runs over a uniform grid with A* pathing, and the unit of navigation is the formation, not the soldier. A formation resolves one path to its destination and carries a set of slots; each soldier's job is to occupy its assigned slot as the formation advances along that path. Individual movement becomes local — hold your place, avoid the man in front — rather than a global search per person.

That decision does three things at once. It collapses thousands of path queries into a handful. It makes cohesion the default instead of something to be recovered afterwards with steering hacks. And it gives the simulation a natural place to express orders: a formation moving, wheeling, charging, rather than four hundred independent agents that happen to be adjacent.

Why a grid

A uniform grid is not the most sophisticated representation available, and that is most of the argument for it. It is trivially queryable, cheap to update when the battlefield changes, and — crucially for a formation-based game — it makes "is there room for a block of men here" a simple question rather than a geometric one. Formations occupy rectangles of cells; placement, blocking and destination validity all fall out of the same structure the pathing already uses.

The cost is granularity: a grid approximates the world, and paths need smoothing to avoid looking like they were drawn on graph paper. That is a solvable presentation problem. An elegant representation that cannot answer formation-shaped questions is not.

Working inside the frame budget

Navigation shares a frame with everything else, so it was profiled alongside the simulation and rendering paths in Unreal Insights rather than in isolation. The optimisation that mattered was structural — moving the query count down by an order of magnitude by pathing formations instead of individuals — not micro-tuning the search itself. That is the general lesson I took from this system: when a cost scales with agent count, the fix is almost never inside the per-agent code.

04 — built, then cut in a design pivot

Settlement designer & economy

Before Greenleaf narrowed to battles, it had a settlement layer: place buildings inside a stronghold, raise walls around it, and run a production-chain economy underneath. I built it. Then the design pivoted and it was cut. It is on this page deliberately — a system you shipped and lost teaches more than one that survived by luck.

What it did

  • Interior building placement. Stronghold-style: the player places structures inside the settlement's footprint, with validity, footprint and adjacency resolved as they drag rather than rejected on commit.
  • Modular wall construction. Walls built from parts rather than placed as prefabs — segments, corners and gates that resolve their own geometry from the path the player draws, so an arbitrary enclosure ends up looking authored.
  • A production-chain economy. Anno-style: raw goods feed intermediate goods feed finished goods, each stage a building with inputs, outputs and throughput. The interesting part is not any single building; it is that a chain has a bottleneck, and the player's job is to find it.

The engineering problem worth talking about

Placement and walls look like art problems and are actually validity problems. Every frame the player is dragging, the system has to answer: does this fit, does it overlap, does it connect, is the resulting enclosure sealed, and what does it cost — fast enough to render the answer as feedback rather than as an error message. That pushed the design toward resolving everything against a grid the settlement already maintained, so questions about space became lookups rather than geometry.

The economy has the opposite shape. It is cheap per tick and hard to reason about, because the behaviour that matters is emergent across the whole graph. Debugging it meant building visibility into the chain — where goods are backing up, which stage is starved — before any of the balancing work was possible.

Why it was cut, and what I took from it

The project narrowed to focus on the battle layer, which was the stronger pillar and the thing that made Greenleaf distinctive. That was the correct call, and the settlement layer was the right thing to lose. I would rather work somewhere that cuts a finished system for a good reason than somewhere that ships everything it starts.

What I took from it is mostly about sequencing. A production economy is only interesting once there is a game around it applying pressure; building it in depth before that pressure existed meant tuning against assumptions rather than against play. Now I front-load the question of what evidence would tell us this system is working, and if the answer is "we won't know for six months", that is worth saying out loud before writing the system, not after.
